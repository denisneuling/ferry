# CI

Three workflows, split by what triggers them. They are websearch's (which are
soulforge's), with the registry folders of the `mdvc` group, so that what is
learned about this Forgejo instance in one repository applies to the others.

| workflow | runs on | does |
|---|---|---|
| `ci.yml` | pull requests, and pushes to develop | secret scan, lint (with the generated API code and the OpenAPI spec), the interface's lint, i18n check, tests and build, tests with the race detector against a Samba the job starts |
| `main.yml` | pushes to main | the checks again; once releases are unlocked, the image from the commit and semantic-release |
| `release.yml` | a `v*` tag, and `workflow_dispatch` | refuse while releases are locked; otherwise validate the tag, test, the tagged image, the Forgejo release, binaries |

The repository starts with the Go service only. The jobs for the parts that
follow are added with them, from websearch's workflows:

- chart lint, render and docs (`helm`), and the charts in `release.yml`,
  with `charts/`.

## Ordering

A cheap check gates an expensive one:

    ci.yml       secret-scan ─┐
                 lint ────────┴─> test, ui

    main.yml     config, secret-scan, lint ─> verify ─┬─> image
                                                     └─> semantic-release

    release.yml  gate ─> validate ─> test ─> image ─> notes ─> binaries

No Forgejo release is made until the image is pushed: `notes` creates it, and a
release whose image does not exist is worse than none.

## Releases are locked

The first release is made deliberately by the maintainer, not by the first
merge to main. Until the repository variable `RELEASES_ENABLED` is set to
`true`:

- `main.yml` runs the checks on main and skips the image and semantic-release;
- `release.yml` fails in its first job, `gate`, whether it was dispatched or
  started by a tag pushed by hand.

Setting the variable is the maintainer's step, taken together with the first
merge to main. Nothing in a pull request can set it.

## Samba in CI

The SMB tests (`internal/smb`) need a Samba. The test jobs (`ci.test`,
`main.verify`, `release.test`) start one themselves: they install the
distribution's `samba` package and run `hack/samba/setup.sh daemon`, the
script `make dev-samba`'s container runs too, so the local and the CI Samba
cannot drift apart. It serves two instances with the same fictional users and
shares — `map to guest = Bad User` on 445, `Bad Password` on 446 — and the
tests find them through `FERRY_TEST_SMB_SERVER` and
`FERRY_TEST_SMB_SERVER_BAD_PASSWORD`. No registry and no third-party image are
involved, so the same steps work on any runner. Without those variables the
SMB tests skip.

## Generated code

`api/v1/v1.gen.go` is committed, so that every tool — `go build`, `go mod
tidy`, Renovate — sees a complete module. The lint job generates it again with
the oapi-codegen `go.mod` pin as a tool and fails when that changes anything;
`api/v1/generate_test.go` checks the same in every test run. The interface's
API client is generated by its npm scripts and not committed. The Makefile
pins golangci-lint, gitleaks, helm-docs and the Redocly CLI, and the workflows
read the versions from there.

## Images

One image, `images/mdvc/ferry`, with the interface compiled in
(`Dockerfile`). It is tagged with the version (releases), `latest`, the full
commit SHA and its twelve-character prefix — what Flux writes into a chart
version's build metadata when a HelmRelease reads the chart from Git, so a
cluster tracking a branch runs the commit it tracks.

The interface uses no `@metapatrol/*` packages, so its build needs no forge
token and no private CA: `npm ci` reads only public packages, through the CI
cache.

## Versions

A breaking change (`feat!:`) raises the minor version, not the major
(`.releaserc.json`). `release.yml` ignores `v0.0.0`, the baseline a first
version is counted from.

## How a release actually happens

Not through the tag. Forgejo raises **no push event for a tag created with an
access token**, so `on: push: tags` never fires for the tag semantic-release
makes. `.releaserc.json` runs `.forgejo/trigger-release.sh` from
semantic-release's `successCmd`, which dispatches `release.yml` directly.
`successCmd` runs only when a version was released.

`on: push: tags` stays for tags pushed by hand, which do raise the event.

## Before the first run

**The runner label.** Every job says `runs-on: docker` — a label, not an image.

**Base images through the registry mirror.** The Dockerfile defaults to the
public images; the image jobs pass the mirror's instead (`--build-arg
GO_IMAGE=$REGISTRY/library/golang:…`) and build with `--tls-verify=false`
because the registry uses the instance's private CA.

**The race detector** needs cgo and a C compiler; the test jobs install `gcc`
when the runner image lacks it.

**Secrets and variables.**

| name | kind | value | needed by |
|---|---|---|---|
| `RELEASES_ENABLED` | variable | `true` once releases are unlocked | `main.config`, `release.gate` |
| `ZOT_URL` | variable | the registry, e.g. `https://registry.example.com` | the image jobs |
| `ZOT_USERNAME` | variable | registry login | the same |
| `ZOT_TOKEN` | secret | registry password or token | the same |
| `AUTOMATION_TOKEN` | secret | Forgejo access token | `main.semantic-release`, `release.notes`, `release.binaries` |

Without the registry values `main.yml` skips the image job rather than failing;
`release.yml` fails, because a release that cannot be published should not pass
quietly.

`AUTOMATION_TOKEN` needs repository write (releases, assets, the changelog
commit and tag) and the right to dispatch workflows. semantic-release pushes
its release commit to main, so a branch protection on main must let this token
through.

**Nothing may be called `FORGEJO_TOKEN`.** The runner injects a variable of that
name holding its own ephemeral token, and it wins over a job env of the same name:
requests then go out as the bot, and cross-repository calls quietly fail.

## The GitHub mirror

The repository is push-mirrored to GitHub. Issues and pull requests opened
there are carried in by forgejo-github-bridge (`CONTRIBUTING.md`). The public
artifacts — `ghcr.io` images, charts and GitHub releases — are built there by
`.github/workflows/publish.yml`, websearch's, which is added with the first
release; until then GitHub builds nothing.

## Layout

    .forgejo/
      README.md             this file
      trigger-release.sh    starts release.yml for the tag semantic-release made
      workflows/            ci.yml, main.yml, release.yml
    .github/
      ISSUE_TEMPLATE/, PULL_REQUEST_TEMPLATE.md

Locally:

    make secret-scan           # the working tree, what CI runs
    make secret-scan-history   # the full history, for an audit
    make lint test
